# Регистрация на мероприятие — backend test assignment

Это небольшой работающий API для регистрации участников на мероприя. В нём есть модели, миграции, seed-данные, HTTP-маршруты и интеграционные тесты.

## Задача

QA сообщает:

> При высокой активности иногда на мероприятие с лимитом 10 человек регистрируется 11 или 12. Кроме того, после сетевых ошибок повторный запрос иногда создаёт повторную регистрацию.

Доведите функционал до состояния, при котором:

- число регистраций никогда не превышает `capacity`;
- у одного пользователя не больше одной регистрации на одно мероприятие;
- первый успешный запрос возвращает `201`, а повтор той же пары event/user — ту же регистрацию с `200`;
- конкурирующие запросы не приводят к неожиданным `5xx`;
- решение остаётся корректным, если запросы обрабатывают несколько процессов API с общей PostgreSQL.

Не тратьте на задачу больше **90–120 минут**. ИИ, документацию и интернет использовать можно и нужно. Будьте готовы кратко объяснить выбранный подход, компромиссы и способ проверки.
Добавьте тесты, которые доказывают корректность решения при параллельных запросах.

## Запуск

Нужен Docker с Compose:

```bash
docker compose up --build
```

API будет доступен на `http://localhost:3000`. Миграции и seed выполняются автоматически.

Прогон тестов в отдельной базе:

```bash
docker compose --profile test run --rm tests
```

Без Docker API можно запустить через `npm ci`, `npm run db:migrate`, `npm run db:seed`, `npm run dev`, предварительно задав `DATABASE_URL`. Для локального запуска тестов имя базы в `DATABASE_URL` должно оканчиваться на `_test`.

## API

```text
GET  /health
GET  /events
GET  /events/:eventId
POST /events/:eventId/registrations   { "userId": "<uuid>" }
```

Пример:

```bash
curl -X POST http://localhost:3000/events/00000000-0000-4000-8000-000000000010/registrations \
  -H "Content-Type: application/json" \
  -d '{"userId":"00000000-0000-4000-8000-000000000001"}'
```

Seed-объекты:

| Тип   | UUID                                                                            | Описание            |
| ----- | ------------------------------------------------------------------------------- | ------------------- |
| Event | `00000000-0000-4000-8000-000000000010`                                          | Открытое, 10 мест   |
| Event | `00000000-0000-4000-8000-000000000011`                                          | Открытое, 1 место   |
| Event | `00000000-0000-4000-8000-000000000012`                                          | Отменённое, 10 мест |
| User  | `00000000-0000-4000-8000-000000000001` … `00000000-0000-4000-8000-000000000025` | 25 участников       |

## Ограничения

Не нужно добавлять аутентификацию, frontend, очередь, кэш, удаление регистраций или API изменения вместимости. Если меняете схему БД, делайте это миграцией, без удаления существующих данных.

## Решение

### Что было сломано

1. **Гонка по вместимости.** `Registration.count()` и `Registration.create()` выполнялись
   без транзакции и без блокировки. Между проверкой и вставкой успевали вклиниться
   другие запросы — классический check-then-act, отсюда 11–12 человек на 10 мест.
2. **Гонка по дубликатам.** `findOne()` → `create()` имел ту же проблему, и в БД
   вообще не было инварианта на пару `(event_id, user_id)` — об этом честно
   говорил комментарий в миграции 001.
3. **Неверный порядок проверок.** Проверка вместимости шла *до* проверки
   идемпотентности, поэтому повтор запроса на заполнившемся мероприятии отдавал
   `409` вместо `200` с исходной регистрацией. Существующий тест это не ловил,
   потому что использовал мероприятие на 10 мест.

### Как починено

Корректность обеспечивает база, а не процесс Node — поэтому решение переживает
запуск нескольких процессов API над одной PostgreSQL.

- **Миграция `002`** добавляет unique-constraint на `(event_id, user_id)`. Это
  жёсткий инвариант: дубликат физически не может появиться, каким бы кодом его ни
  вставляли. Миграция сначала ищет уже существующие дубликаты и при их наличии
  падает с понятным сообщением и списком пар — ничего не удаляя.
- **`registration-service`** выполняет всю операцию в одной транзакции и начинает
  с `SELECT ... FOR UPDATE` по строке мероприятия. Блокировка строки сериализует
  попытки регистрации на *это* мероприятие, поэтому «посчитать места → вставить»
  становится атомарным. Разные мероприятия друг друга не блокируют.
- **Порядок проверок**: событие → пользователь → идемпотентность → вместимость.
  Повтор успешного запроса возвращает `200` даже когда мест уже нет.
- **`UniqueConstraintError`** перехватывается и превращается в `200` с
  существующей регистрацией, а не в `5xx`. При текущей блокировке этот путь
  недостижим, но он оставлен как страховка на случай обхода блокировки.
- **Валидация входа**: некорректный uuid раньше доходил до PostgreSQL и давал
  `500`; теперь это `400 VALIDATION_ERROR`.

### Компромиссы

- Блокировка строки мероприятия сериализует регистрации **на одно мероприятие**.
  Для лимита в десятки/сотни мест это незаметно (транзакция — единицы
  миллисекунд), зато логика остаётся тривиально читаемой. Если однажды
  понадобится более высокая пропускная способность на одно мероприятие,
  следующий шаг — денормализованный счётчик `registered_count` с
  `UPDATE ... WHERE registered_count < capacity`, который вообще не блокирует
  конкурентов. Это уже требует поддержания счётчика в консистентном состоянии,
  поэтому для текущих требований выбран более простой вариант.
- Альтернатива через `SERIALIZABLE` + ретраи отвергнута: она перекладывает на
  приложение обработку `40001` и усложняет код без выигрыша на этой нагрузке.
- Избыточный индекс `registrations_event_id_idx` оставлен: unique-constraint его
  покрывает, но удаление индексов не входит в задачу.

### Как проверялось

- `tests/concurrency.test.ts` — параллельные всплески запросов: 25 пользователей
  на 10 мест, 25 на 1 место, два мероприятия одновременно, 20 одинаковых
  повторов, 75 запросов с повторами, регресс-тест на `200` после заполнения,
  плюс отменённые мероприятия (одиночный запрос, всплеск из 25 запросов и
  повтор после отмены).
- `tests/multi-process.test.ts` — поднимает **три настоящих процесса API** на
  разных портах над одной PostgreSQL и стреляет в них по кругу. Это отличает
  инвариант в базе от случайной сериализации внутри одного пула соединений.
- Тесты проверены на «обратную чувствительность»: если вернуть исходный
  контроллер, падают 12 тестов из 25; если убрать проверку статуса — ещё 3.

### Отменённые мероприятия

Регистрация на мероприятие со статусом `CANCELLED` раньше проходила успешно —
проверки статуса в коде не было вообще. Теперь такой запрос получает
`409 EVENT_CANCELLED`.

Проверка стоит **после** ветки идемпотентности, а не перед ней. Иначе отмена
мероприятия задним числом ломала бы уже работавшие повторы: клиент, который
успешно зарегистрировался и повторяет запрос после сетевой ошибки, получил бы
ошибку вместо своей же регистрации. Новых строк при этом не создаётся — отмена
закрывает только создание регистраций, а не чтение существующей.
